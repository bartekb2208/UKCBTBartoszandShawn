Plan: a graph-feature ranker with a rule layer

One approach aimed at the headline score (100 × Average Precision on the test set) and at the written criteria: reproducibility, a clear method, honest limits. Submission closes 16:30 London.

Recommendation

Build a transaction-level ranker in LightGBM on wallet and graph features, add a small set of readable rules for the report, and rank-blend a wallet-level view into it. Validate with 5-fold grouped cross-validation so the score we see tracks the test score. No model touches the data until this plan is agreed.

Primary objectiveMaximise AP on the 40,101-row test set
Main risk~20,000 normal "relay" rows that look like laundering
Validation5-fold grouped, plus leave-one-family-out
Hard stopFinal upload by 16:00, deadline 16:30

The six judge ideas are not six projects. Five of them become feature families feeding one model, and the sixth (the LLM case writer) only helps the pitch. That keeps the work in one reproducible pipeline.

5-fold validation

The goal is a fold score that predicts the test score. The test set has unseen wallets and variations, so folds must not share wallets or scenarios.

Main score: 5-fold grouped, stratified

  • Group rows that share wallets so a pattern never straddles train and fold.
  • Planted rows group by scenario_id. Normal rows group by wallet cluster.
  • Stratify on the positive label so each fold holds about 250 positives.
  • Fixed seed, assignment saved to disk and reused for every experiment.
  • Report mean AP and per-fold spread. A change smaller than the spread is noise.

Stress test: leave one family out

  • Hold out a whole family (for example cycle, then multi_stage) and fit on the rest.
  • The drop shows which features carry over to unseen variations.
  • Used to choose features, not to report the headline score.

Shift check, labels unused

  • Train a classifier to separate train/ from validation/ on features only.
  • Features that separate them easily are shift risks. Drop or rescale them.
  • Split identity is never a model feature.

Open design question, first task of the day. In a one-week network with exchange and payroll hubs, wallet connected components may merge into one giant group, making wallet grouping useless. Fix: build components after removing very high-degree hubs, and fall back to scenario_id for planted rows. Check the component size distribution before fixing the fold rule.

Rules for ourselves

  • Build graph features once over the whole train split, exactly as will be done for test. Folds split only the model fit.
  • Choose features, model and hyperparameters from fold scores only. Cap the number of ideas tried against one fold set.
  • Seal one or two families as a final check, used once before freezing.
  • Choose any rule threshold inside the training folds, never on the fold it is scored on.
  • A feature that looks too good needs an explanation. It may be a generator artefact such as amount precision or ledger-index patterns.

Model stack

Layer 1: LightGBM ranker

Gradient-boosted trees on the full feature set. Try the binary objective first, then a ranking objective, and keep whichever has the higher fold AP. Class weighting tuned inside folds.

Layer 2: wallet-level view

Score wallets and clusters on aggregated features, project each wallet's score onto its transactions, and rank-blend with Layer 1. Out-of-fold only, so nothing leaks through the neighbour features.

Layer 3: readable rules

Five to eight one-line flags such as "forwarded 90% within 10 minutes". Used in the report and as a small blend term only if they raise fold AP.

Baseline to beat: the starter notebook (logistic regression on 12 simple rules). We run it under our own folds first so every later number has a reference.

Final output: rank-normalise the blend into [0, 1] with unique values, one row per test transaction.

Brief for the Opus session

To paste into the VS Code session that builds this. It carries the constraints so they are not rediscovered.

Goal: maximise 100 x Average Precision on the 40,101-row test set.
Data: decode-and-detect-training-data/train (labelled) and
      validation (unlabelled). Test goes in test-data/. Never commit data.

Constraints
- Score one row per TRANSACTION_HASH, scores in [0,1], no ties.
- Features must be behavioural. No wallet identity. Split origin is
  not a feature. Organiser data only.
- Compute graph features once over a whole split (as for test);
  folds split only the model fit.
- 5-fold stratified grouped CV. Groups: scenario_id for planted rows,
  hub-aware wallet clusters for the rest. Save the fold map to disk.
- Also run leave-one-family-out. Seal two families for one final check.
- Report AP overall and per family on every run.
- Reproducible: seeds, pinned deps, one run.sh. Keep AI_USE.md updated.

Order of work
1. Loader + USD valuation (see payments.py) and fold map.
2. Starter-notebook baseline under our folds = number to beat.
3. Add feature families one at a time; keep only gains above fold spread.
4. LightGBM, then wallet-level blend, then rank-normalise.
5. Reproduce from a clean checkout before any final upload.
